# الأمن السيبراني - منصة الكليات في إب

## المخاطر الأمنية المحتملة
- **اختراق بيانات المستخدمين**: تسرب البريد الإلكتروني وكلمات المرور.
- **تخريب قاعدة البيانات**: حذف أو تعديل بيانات الكليات.
- **هجمات تعطيل الخدمة (DDoS)**: تعطيل المنصة في مواسم التقديم.
- **اختراق جلسات المستخدمين**: انتحال هوية المستخدمين.

## التدابير الأمنية

### أمن التطبيق
- تعقيم المدخلات (Input Sanitization) لمنع XSS و SQL Injection.
- استخدام ORM بدلاً من الاستعلامات المباشرة لمنع حقن SQL.
- CSRF Tokens للنماذج الحساسة.
- Helmet.js لإعدادات الأمان في HTTP headers.
- Rate Limiting (100 طلب/دقيقة) لمنع هجمات القوة العمياء.

### أمن كلمات المرور
- تشفير بكلمة باستخدام bcrypt مع 10 Salt Rounds.
- فرض كلمة مرور قوية: 8 أحرف على الأقل، حرف كبير وحرف خاص ورقم.
- لا لتخزين كلمات المرور بنص واضح (Plain Text) أبداً.
- إضافة 2FA (مصادقة ثنائية) للحسابات الحساسة (مشرفي النظام).

### أمن الجلسات
- JWT مع توقيع قوي (HS256 أو RS256).
- صلاحية قصيرة للـ Token (24 ساعة).
- Refresh Token للجلسات الطويلة.
- تخزين الـ Token في HttpOnly Cookies (وليس Local Storage).
- تسجيل الخروج التلقائي بعد 30 دقيقة من عدم النشاط.

### أمن البيانات
- تشفير قاعدة البيانات في وضع السكون (Encryption at Rest).
- HTTPS حصرياً (TLS 1.3).
- نسخ احتياطي يومي مشفر.
- سياسة الاحتفاظ بالبيانات: حذف بيانات المستخدم بعد طلب الحذف.

### أمن الخادم
- تحديث منتظم لجميع الحزم (npm audit أسبوعياً).
- جدار ناري (Firewall): UFW.
- منع تسجيل الدخول SSH بكلمة مرور (استخدام SSH Keys فقط).
- مراقبة السجلات (Log Monitoring) للكشف عن الاختراقات.

## خطة الاستجابة للاختراق
1. عزل الخادم المخترق.
2. تغيير جميع كلمات المرور والمفاتيح.
3. استعادة البيانات من النسخة الاحتياطية.
4. إبلاغ المستخدمين المتأثرين.
5. توثيق الحادثة وتحليل السبب الجذري.
